## 4. 阅读仓库的检查清单

1. 是否有LICENSE文件？根目录许可证是否覆盖图片、模型、音频、字体和子模块？
2. 赛事来源是官方参赛链接、作者自述、还是普通GitHub仓库？获奖信息是否有主办方佐证？
3. README能否在干净环境启动？是否缺模型、API Key、数据集、云资源或私有依赖？
4. Demo入口在线吗？这是页面可加载还是完整交互经过实测？本文明确标注未测试摄像头授权的Demo。
5. 提交历史和测试是否能证明项目状态？单纯commits/Stars不代表可运行或质量。
6. 先学结构和玩法，再自己实现；未经许可不要复制代码/素材，也别把仓库里的Agent配置带入不同平台。

### 寻踪源码阅读笔记（基于公开仓库）

- `server/api/generate-review.post.ts`：将`journeyLog`、`unlockedGallery`交给一次OpenAI-compatible `chat.completions.create`，`temperature: 0.8`、`max_tokens: 800`，输出旅程回顾；这是“游戏状态由代码驱动、AI负责结尾内容”，不是每帧调用模型。
- `nuxt.config.ts`把`NUXT_OPENAI_API_KEY`、`NUXT_OPENAI_BASE_URL`、`NUXT_OPENAI_MODEL`放在服务端`runtimeConfig`；默认Base URL为DeepSeek API，默认模型`deepseek-chat`。`README.md`要求通过`.env.example`配置密钥。比赛里只能换成主办方允许的模型/密钥管理方式。
- `server/api/events.get.ts`从`data/events.csv`加载事件并解析，说明内容/事件表可以与游戏代码分离，便于短赛并行写内容与功能。
- 可借鉴：Agent工作单明确事件状态输入和最终输出；模型响应慢时游戏回合已完成，不需要阻塞实时玩法；README交付环境/启动/目录结构。
- 代码审阅提示：该API可见版本没有明显的请求Schema校验、限流、输出长度二次校验；把用户可控文本插入XML prompt前未做专门转义。若照这个思路重做，应校验旅程记录结构、限制字段数量/长度、转义/分隔不可信文本、设置超时和静态回顾兜底，并避免泄露服务端密钥。此为本仓库静态阅读发现，不代表已运行安全测试。

## 6. 小红书VibeCoding金奖作品：拓扑五子棋（公开源码）

- 项目：[YinkaiYu/topology-gomoku](https://github.com/YinkaiYu/topology-gomoku)。小红书官方获奖公告列人文知识赛道金奖《拓扑五子棋》；GitHub README的“活动与荣誉”也自述获小红书VibeCoding大赛金奖，名称和赛道相符。官方公告未直接链接该仓库，归属证据强但链路不是主办方直链。
- 根目录LICENSE为MIT；GitHub显示222 commits，README版本1.44.1。`package.json`为Node.js >=18，纯HTML/CSS/JavaScript风格的`app/index.html`和`app/assets/*.js`，多平台发布脚本；这是经过长期迭代的产品，不是小型48小时作品。
- 核心玩法：在七种拓扑棋盘（平面、圆柱、环面、莫比乌斯带、克莱因瓶、实射影平面、球面）玩五子棋；支持人机、离线本地双人；由教程线路、关卡解锁和可拖动二维/三维转换把拓扑概念做成可玩知识。
- 结构可读：`app/assets/topology.js`、`game-controller.js`、`game.js`、`board-view-logic.js`、`topology-morph.js`等；`tests/`含拓扑规则、边界、棋盘转换、双人离线、回放等测试；根目录有`AGENTS.md`和`docs/`开发/设计/发布文档。
- 可借鉴：用单一熟悉规则承载新机制；逐关解锁并在交互中解释；状态机和拓扑逻辑可测试；使用测试和清晰的Agent工作约定支撑长期迭代。仓库含`licenses/`、字体和图像资源，MIT根许可证不应替代对每个素材/字体的许可核查。
- `package.json`列出`npm test`、`npm run validate`、`npm run docs:check`等脚本；这里只阅读了仓库文件，未克隆/运行或声称测试通过。
