## 2. 跨工具通用的Agent指引结构

可以将项目指引分成“稳定的项目事实”和“短期任务单”：

1. **项目目标与受众：**一句话说明产品解决什么问题、谁会用。
2. **代码地图：**入口、主要目录、已有技术栈，不要让Agent重新发明架构。
3. **可验证命令：**已实际运行过的安装、启动、测试、构建命令；标注尚未验证的命令。
4. **边界：**可改文件、不允许改文件、依赖和API限制、数据/素材许可约束。
5. **接口契约：**模块输入/输出、状态、事件格式和错误处理。
6. **质量门槛：**功能验收、测试路径、人工浏览器/设备检查方式。
7. **失败策略：**依赖不可用、连续失败、测试失败时如何停止、保留基线并报告。
8. **交付报告：**改动文件、运行命令及真实结果、已知限制、未完成项。

根目录指引应短、稳定、可复用；某个具体功能/一夜任务放在独立工单中，避免把当前临时任务写成长期规则。

## 3. 赛事短任务的建议格式

每一条Agent任务至少包含：

- **目标：**要让用户看到什么行为，不只写“优化一下”。
- **允许修改范围：**列出文件/目录；未列的不要顺手重构。
- **基线与保留项：**当前可运行版本、不能破坏的主链路。
- **接口/约束：**输入、输出、依赖、数据处理、许可、API权限。
- **验收步骤：**可手动重复的步骤及预期结果；成功标准不能只写“代码完成”。
- **验证：**要跑的命令、浏览器操作、人工检查；没有执行的测试如实标记。
- **失败/停止条件：**重复同类错误达到预设次数后停，保留错误信息和基线，不扩大改动。
- **交付说明：**变更文件、测试结果、风险、后续建议。

## 4. KCoder夜间Agent的边界

- 普通会话完成一次回答，不等于夜间任务正在持续运行；保存工作流不等于执行成功；定时任务可能建立新会话、等待审批、消耗额度。离场前确认任务实际启动、目标在线、额度和停止条件。
- 规则规定远程只经获准KCoder连接器（飞书/企业微信）；第三方远控不合规。指南中的移动Web/App/HTTPS中继跨端能力需要技术组确认，不能自行当成允许路径。
- 不把密钥写入提示词、源码或截图；把它放在批准的密钥配置处。外部模型、API、MCP、依赖下载须先确认赛事允许。
- Agent没有真实验证就不能声称“测试通过”；应交付未通过的命令、原始错误和最近一个可运行版本。

## 5. 安全与许可

- 把“执行命令、联网、部署、删改数据、上传文件、加依赖”等能力区分开，按最小需要授权；项目说明文本不是沙箱。
- 不向Agent提供不必要的个人信息、摄像头原始画面、商业秘密或API密钥。
- 第三方代码、模型、图片、音频和字体分开记录来源和许可；“GitHub公开”不代表MIT或可再发布。
- 先确认赛事政策再引入外部Agent、MCP Server、模型API或远程控制工具。

## 6. 一份简版短任务Prompt

```text
目标：<具体用户行为和可观察结果>
允许修改：<目录/文件白名单>
不得破坏：<已有主链路、接口、运行方式>
上下文：<项目入口、当前状态、参考文档>
约束：<依赖/网络/许可/隐私/API/平台规则>
接口：<输入/输出/状态/事件格式>
验收：<按顺序操作，列出预期结果>
验证：<实际要执行的命令和人工检查>
停止条件：<重复错误次数、无法解决时应保留什么并报告什么>
交付：<改动文件、测试结果、未完成项、风险>
```
