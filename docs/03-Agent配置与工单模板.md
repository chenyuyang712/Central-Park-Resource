## 2. 跨工具通用的Agent指引结构

可以将项目指引分成“稳定的项目事实”和“短期任务单”：

1. **项目目标与受众：**一句话说明产品解决什么问题、谁会用。
2. **代码地图：**入口、主要目录、已有技术栈，不要让Agent重新发明架构。
3. **可验证命令：**已实际运行过的安装、启动、测试、构建命令；标注尚未验证的命令。
4. **边界：**可改文件、不允许改文件、依赖和API限制、数据/素材许可约束。
5. **接口契约：**模块输入/输出、状态、事件格式和错误处理。
6. **质量门槛：**功能验收、测试路径、人工浏览器/设备检查方式。
7. **失败策略：**依赖不可用、连续失败、测试失败时如何停止、保留基线并报告。
8. **交付报告：**改动文件、运行命令及真实结果、已知限制、未完成项。

根目录指引应短、稳定、可复用；某个具体功能/一夜任务放在独立工单中，避免把当前临时任务写成长期规则。

## 3. 赛事短任务的建议格式

每一条Agent任务至少包含：

- **目标：**要让用户看到什么行为，不只写“优化一下”。
- **允许修改范围：**列出文件/目录；未列的不要顺手重构。
- **基线与保留项：**当前可运行版本、不能破坏的主链路。
- **接口/约束：**输入、输出、依赖、数据处理、许可、API权限。
- **验收步骤：**可手动重复的步骤及预期结果；成功标准不能只写“代码完成”。
- **验证：**要跑的命令、浏览器操作、人工检查；没有执行的测试如实标记。
- **失败/停止条件：**重复同类错误达到预设次数后停，保留错误信息和基线，不扩大改动。
- **交付说明：**变更文件、测试结果、风险、后续建议。

## 4. KCoder夜间Agent的边界

- 普通会话完成一次回答，不等于夜间任务正在持续运行；保存工作流不等于执行成功；定时任务可能建立新会话、等待审批、消耗额度。离场前确认任务实际启动、目标在线、额度和停止条件。
- 规则规定远程只经获准KCoder连接器（飞书/企业微信）；第三方远控不合规。指南中的移动Web/App/HTTPS中继跨端能力需要技术组确认，不能自行当成允许路径。
- 不把密钥写入提示词、源码或截图；把它放在批准的密钥配置处。外部模型、API、MCP、依赖下载须先确认赛事允许。
- Agent没有真实验证就不能声称“测试通过”；应交付未通过的命令、原始错误和最近一个可运行版本。

## 5. 安全与许可

- 把“执行命令、联网、部署、删改数据、上传文件、加依赖”等能力区分开，按最小需要授权；项目说明文本不是沙箱。
- 不向Agent提供不必要的个人信息、摄像头原始画面、商业秘密或API密钥。
- 第三方代码、模型、图片、音频和字体分开记录来源和许可；“GitHub公开”不代表MIT或可再发布。
- 先确认赛事政策再引入外部Agent、MCP Server、模型API或远程控制工具。


## 7. 从公开获奖项目提炼的AI调用边界

### 参考：寻踪（公开代码，获奖归属为作者自述）

- 项目README自述THC 2025 AI Coding赛道二等奖，仓库MIT，14 commits并已归档；赛制/奖项尚缺独立官方页面佐证，按作者自述引用。
- AI只在旅程结束时收到`journeyLog`与`unlockedGallery`，生成旅行回顾/环保建议；场景探索、选择、收集由CSV事件表和程序状态机驱动。这种“确定性核心 + 低频AI润色”很适合短时Demo，也能让AI失败时保住主链路。
- `nuxt.config.ts`使用服务端runtime config读取`NUXT_OPENAI_API_KEY`、`NUXT_OPENAI_BASE_URL`、`NUXT_OPENAI_MODEL`；密钥留在服务端环境变量，不放客户端代码。其默认OpenAI兼容入口/DeepSeek配置仅是该仓库范例，不能照抄到训练营；应使用技术组指定模型与凭据。
- API示例对请求字段和模型文本未做足够严格校验；训练营实现应增加Schema、字段长度、超时/额度控制、失败回退文案和日志脱敏。使用外部API前先核对赛事许可。

### 把AI玩法访谈转成Agent工单

《觉醒AI》获奖页和《喵呜岛》社媒自述都强调AI应进入游戏核心体验，但可直接复用的项目源码没有确认。Agent任务应明确写出：

1. AI解决的玩家问题/参与的玩法决策，而非泛写“增加智能”。
2. 一局中何时调用模型，传递的最少状态字段，预计响应时延和超时路径。
3. 游戏状态由谁持有；模型输出不得直接改变未校验的分数/金币/胜负。
4. 输出格式、枚举/长度限制、错误和超时的静态回退值。
5. 对应文件范围、至少一条完整验收路径、人工演示方式和额度上限。

```text
目标：让玩家完成一局后得到根据本局事件和收集物生成的个性化回顾。
边界：游戏状态仍由本地状态机维护；模型输出不能改分数、事件或解锁状态。
输入：仅传本局最多N条预定义事件ID/选项ID与已解锁物种ID；禁止原始个人信息。
输出：JSON {title, recap, suggestion}，各字段限长并经Schema校验。
失败回退：超时、429、无密钥或解析失败时显示预设回顾，玩法继续。
验收：模型成功、超时、错误格式、空日志四种情况下都能结束本局并可继续下一局。
```

## 8. 成熟参赛仓库的Agent协作规范样例

[拓扑五子棋](https://github.com/YinkaiYu/topology-gomoku)根目录的`AGENTS.md`约束贡献者与维护者权限、独立分支/worktree、预览/验收后再合并、平台适配边界、必须运行的测试/文档校验。可借鉴的不是照搬全部流程，而是将这些稳定规则分层：

- 项目指引写长期架构、权限、测试命令和平台边界；单项Agent任务另写目标、改动范围、验收和交付。
- 要求Agent先读项目文档/检查状态，不能以“改完代码”冒充测试通过；没有运行的命令明确标记未验证。
- 小项目可简化分支/worktree流程，但要保留“先基线、后改动、再验收、用户确认后发布”的顺序。
- 该仓库的`npm test`、Windows PowerShell平台构建脚本及发布分支约束属于它自己的技术环境；不能直接当成KCoder或本赛事的必需配置。此处只提炼公开文档结构，不复制整个外部`AGENTS.md`。
